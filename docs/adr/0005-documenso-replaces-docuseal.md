# 0005 — Self-hosted Documenso replaces DocuSeal

**Status:** Accepted (built: Phase 3 core signing, Tasks 3.31–3.33 and their reviews) · **Date:** 2026-10-06 · **Finalised:** 2026-10-08 (Task 3.35) · **Design:** [D4](../plans/2026-10-06-foundation-rebuild-design.md#decisions-taken), [§6](../plans/2026-10-08-phase-3-shared-services-design.md#6-e-signature-coresigning) · **Plan:** [P3-3, P3-19, P3-26, P3-30, Tasks 3.31–3.33](../plans/2026-10-08-phase-3-shared-services-plan.md) · **Code:** migrations `20261008073909_core_signing`, `20261008082519_core_signing_function_support`, `20261008124818_core_signing_capture`; `_shared/{signing,signing-events,documenso}.ts`; functions `signing-webhook`, `signing-sync`, `signing-test-connection`, `signing-test-document`; CLAUDE.md §7

## Context
Legacy signed contracts through DocuSeal; `docuseal-create-submission` could be called by any signed-in user. PS Hub already runs a hardened Documenso integration (webhook with constant-time secret check, events claimed once). Clinic contracts and consents contain personal information (Loi 25) and must carry the clinic's branding.

## Decision
- E-signature uses **Documenso**, on a **separate self-hosted instance for the clinic** (e.g. `sign.cliniquemana.com`), not Pergolas Signature's. The URL is in `signing_settings`, the API key and webhook secret are org secrets in Vault (ADR 0004), never in code.
- **No `signing-create` function.** Module functions call `createSignatureRequest` in `_shared/signing.ts` (Professionnels 4d), as `signing-test-document` does with the built-in test document. That module renders the PDF on the server (ADR 0008), so only request-creating functions import it; the webhook and the sync use the render-free `_shared/signing-events.ts`.
- **Documenso sends the signing emails** (P3-3: `distributionMethod: EMAIL`, French, the template version's subject and message, sequential when there are several signers). The app sends no `contract.sent` email.
- **Templates** (`document_templates`, versioned draft → published → archived) are created with `settings.manage`; versions are edited by the template's `edit_permission`.
- **One open request per subject and purpose** (`signature_requests_open_subject_idx`): a new idempotency key for a record with an open request is refused until the old one is cancelled. The same key always returns its row, and with other signers is refused.
- **Signers are role-keyed:** a role is unique per request, Documenso recipients are recorded as `[{role, recipient_id}]`, and a recovered document's recipients are matched by signing order (sound because a key's stored orders are the ones every send used).
- **The send claim:** `begin_signature_request_send` allows one send per request at a time (a fresh claim → 409 « Un envoi est déjà en cours. »). A re-send (« Renvoyer ») settles the earlier document first: COMPLETED → recovered, nothing sent again; DRAFT or PENDING → cancelled (a failed cancel stops the re-send); cancelled, rejected or gone → sent again, and the earlier id is superseded.
- **Webhook** (`verify_jwt = false`): `?org=` → that org's secret, none → 401; `timingSafeEqual` on `X-Documenso-Secret` (PS Hub's `!==` fixed); body ≤ 256 KB; `claimEvent` on `<EVENT>:<doc>[:<version>]` with `{ event, document_id, external_id }` only. `apply_signing_event` finds the row in that org, gates the module, and answers `retry` (409, Documenso retries) for a draft whose send is under way.
- **State machine:** monotonic, terminal states never move. Once `DOCUMENT_COMPLETED` is recorded (`completed_event_at`) a signed contract is protected: no expiry, no cancel, rejected and cancelled events ignored, and the signed PDF is downloaded whatever the expiry. `recover_signature_request` adopts a draft Documenso completed only for the request's own document: `externalId` = the request id (checked by the functions) and the draft's recorded document id (checked by the RPC).
- **Signer emails stay hidden from clients:** `signature_request_signers` is granted column by column without `email`, the audit trail redacts `email` and `name`, and no log, claim, report or answer carries an address.

## Consequences
- Jonathan provisions and operates the clinic instance (Mise en service 4).
- `signing-sync` runs « Synchroniser » (caller's RLS read) and the hourly `core.signing_reconcile` job (daily until `…_core_signing_capture`; expire overdue requests after a last sync, settle drafts under their claim).
- **Residual risks, made visible rather than silent:** a double « Renvoyer » sends one document (the claim); a draft Documenso completed whose recipients do not match is reported `signing_orphan_completed` and left for a person; a document under another `externalId` is reported `signing_foreign_document`, never recovered nor cancelled; a completion after the clinic closed a request is reported `signing_completed_after_close`.
- **Before real use (Mise en service 4):** check every `// VERIFY` endpoint of `_shared/documenso.ts` against the instance's OpenAPI, and confirm that the document read returns `externalId` (string or null, never omitted) and each recipient's `signingOrder`, `signingStatus` and `readStatus`.
- DocuSeal code stays in `_legacy/` only as a reference.
- The configured URL is a place the server sends the API key, so it is constrained (P3-34, Task 3.34 review): `https://` to a public DNS name only (the database refuses IP literals and private names), no redirect followed, the host resolved before every request and refused when any address is private, loopback, link-local, CGNAT, multicast or unspecified (local dev excepted: the fake at `host.docker.internal`, only when `APP_URL` is local). Changing the address's origin deletes the stored key, so it is typed again for the new instance. A DNS-rebinding window remains between that check and `fetch`'s own lookup; https and no redirects narrow it.

## Pas de sauvegarde de la VM Documenso
*Added 2026-10-08, migrations `20261008124818_core_signing_capture` and `20261008130552_core_signing_blind_alert`.*

The clinic's Documenso VM is **not backed up**. Rule: every document Documenso produces is copied into our private storage (`signed-documents`, purpose `signing_signed`) as soon as it exists; a Documenso link or id is never the only copy.
- **What is copied:** the signed PDF (`GET …/download?version=signed`), which carries the fields' values and the pages Documenso appends when it seals it: the signing certificate, and the audit log when the instance's document preferences include it (Mise en service: turn both on and check them on the stored test PDF). Everything else we need is already ours: the rendered source PDF (`signing_source`, stored before the send), each signer's viewed / signed / rejected times and the rejection reason (`signature_request_signers`, `signature_requests`), and the signed file's SHA-256. What stays only on the VM is operational (Documenso's copies of its signing emails and its own event log beyond the appended pages); losing it loses no contract.
- **Within the hour, in rotation:** `signing-webhook` stores the PDF on `DOCUMENT_COMPLETED` (a failed store answers 500 and Documenso retries). The net is `core.signing_reconcile`, now **hourly** (`50 * * * *`), which reads **every** sent or viewed request (not only those over a day old). Polling is the only way to see a completion whose webhook never came, so an hour between polls is the cost of the rule: about one Documenso read per open request per hour, bounded by one open request per record and purpose and an expiry of at most 60 days (7 by default), so roughly one read per professional per hour while a contract is out (~50 at most, usually a handful). A run reads at most 100 requests and starts no new batch after 90 s, so with more open requests some wait: the list puts the requests Documenso completed without a stored PDF first, then the **least recently attempted** (`signature_request_syncs.attempted_at`, stamped by `record_signature_sync` after each attempt), so every request is read within a few runs. A completion whose webhook was lost is not known before its read and sorts like any other request: the rotation bounds its wait, and the coverage notice below catches a request no read reaches. Drafts keep their clocks (an hour with a document, a day without), now honoured within the hour.
- **One bad request is not an outage; every document gone is:** a request that fails on its own (deleted at Documenso → 404, a signed PDF over 20 MB, another instance's document) is counted in the run's detail (« N demandes non vérifiées ») and the run stays `ok`. A run counts as having read Documenso only when a read returned a request's own document (`trackOwnReads`; a draft skipped as `sending` does not count). When nothing was read, the run fails as `reconcile_failed` if a failure says Documenso itself is unusable (key refused or not configured, no answer, a redirect, 408, 429, 5xx: `isDocumensoOutage`), or as `reconcile_documents_missing` if at least two requests failed and every one with a 404, another client error or another document under its id (`isDocumentMissing`): a key of another Documenso team, or a VM rebuilt without its documents, the disaster this section is about. A single missing document stays a partial run (more likely deleted there). We chose this rule over an extra « ping » when nothing was read: the ping lists the key's own team, so it answers 200 both for a key of another team and for a rebuilt instance with a new key, and cannot tell those apart from « these documents are gone »; the rule needs no extra call. Failure codes are distinct (`failureCode`): `provider_not_found` (404), `provider_rejected` (another 4xx), `provider_unreachable` (no answer), `provider_error` (the rest), `not_configured`, ours (`signing_foreign_document`, …). The 404 test is one helper (`isProviderNotFound`), to move to the client's `notFound` flag with the envelope API. Per-request Sentry reports (the failure, `signing_orphan_completed`, `signing_foreign_document`, …) go out at most once a day per request and code (`signature_request_syncs.reported`); when the record itself fails, they go out unthrottled. A manual « Synchroniser » of a sent or viewed request is recorded too (`record_signature_sync`, nothing reported), so a successful click clears its « non vérifiée » state.
- **A person hears of a failure:** `core.signing_unsaved_alert` (SQL maintenance job, hourly at `:55`, in the database so it still runs when the edge function, `pg_net` or Documenso fails) posts one important notice (« À surveiller », the bell; holders of `settings.integrations_manage`; linked to « Signature électronique ») for each request and Documenso document that Documenso completed over 6 hours ago whose signed PDF is still not stored, and for each draft left `orphan_completed` (completed at Documenso, recipients unmatched: needs a person). Dedupe key `<request id>:<document id>`; it expires once the request no longer meets that condition (signed, the orphan cancelled or re-sent), and a later document of the same request is a new notice.
- **A person hears of a completion we cannot see** (`…_core_signing_blind_alert`, the same job, so the same audience and timing; one kind per case because each dedups and resolves differently; each case in its own block, so one that fails is logged by its SQLSTATE and the others still run):
  - `core.signing_reconcile_failing`: an org has a sent or viewed request of an enabled module, sent over 6 hours ago, and `core.signing_reconcile` has had no `ok` run for it in the last 6 hours (or none at all). Since a partial run is `ok`, this means Documenso unreachable or the key refused (`reconcile_failed`), every document gone (`reconcile_documents_missing`), the function down (`http_*`, `no_response`, `configuration_missing`), or `pg_net` stuck. A healthy run always logs `ok`, even with nothing to follow, so a quiet clinic never trips it. The notice says the address, the key or the instance may be wrong. One notice per org and outage (dedupe key = the org's last `ok` run id, `none` if there is none), no subject (it names no request); it expires at the first alert run after an `ok` run finished, and the next outage, after a newer `ok` run, gets a new key and a new notice.
  - `core.signing_requests_unverified`: the reconcile works for the org (an `ok` run in the last 6 hours) but a request of an enabled module with a Documenso document and no known completion has not been read successfully for 6 hours (a sent or viewed one whose last successful read, else its send, is over 6 hours old; a draft failing to settle for over 6 hours). « Une ou plusieurs demandes n'ont pas pu être vérifiées »: a request failing on its own, one the runs never reach, or (a clinic with a single open request) a wrong address, key or instance, so the notice no longer claims the reconcile works. It links to « Signature électronique », where holders of `settings.integrations_manage` see the list (`list_unverified_signature_requests`, definer, the caller's org, the same condition as the notice: `private.signing_unverified_requests`): each request's title (only when the caller may see the request, else its module), its last successful read, since when it fails and the failure in plain French; hidden when empty. No entry links anywhere yet: no record type that signs has a page. One notice per org and episode (dedupe key `after:<previous notice id>`, `first`), posted when the previous one has expired; it expires once every request is read again.
  - `core.signing_module_disabled`: the module of a sent or viewed request has been disabled for over 6 hours. Its webhooks and the reconcile skip it (module gate), so a completion is never stamped and its PDF waits on the VM. The switch-off time is `org_modules.disabled_at` (moved only by a switch; `updated_at` moves on every save). One notice per org and switch-off (dedupe key `<module>:<epoch of disabled_at>`), linked to « Modules »; re-enabling needs `modules.manage`, so the notice tells integration managers to ask a person who manages the modules. It expires once the module is enabled again (or no sent or viewed request of it is left).
  - **Deploy guard:** the outage and coverage cases wait until the job is 6 hours old (its catalogue row), so the first runs after the push, before 6 hours of hourly reconciles, post nothing false.
- **Residual gaps, known:** `pg_cron` itself stopped (the alert job does not run either: the cron runs' absence in « Tâches planifiées » is the only sign); an outage of over 90 days purges the last `ok` run, so its key falls back to `none` (no second notice if one with that key already exists). A request only 6 hours old or less is not counted, so a failure that starts with it is announced at most 6 hours after it was sent.

## Alternatives
- **Keep DocuSeal:** no hardened integration to port; legacy one had an authorization hole.
- **Share PS Hub's Documenso instance:** mixes two companies' data and branding (Loi 25).
- **A generic `signing-create` function** (this ADR's first version): design §6.3 has each module's function call the shared library behind its own permission and module checks (plan inconsistency #13).
- **Our own signing emails:** sequential signing would need our own relay of Documenso's turn-taking (P3-3).

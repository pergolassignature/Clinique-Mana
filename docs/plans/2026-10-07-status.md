## Avant la fusion

**Vérification de staging en lecture seule (avec ton feu vert)** : les droits sur Vault et les extensions dont dépendent les migrations. Rien n'est modifié ; à lancer dans l'éditeur SQL de staging.

```sql
select extname, extversion, extnamespace::regnamespace from pg_extension where extname in ('supabase_vault','pgcrypto','btree_gist','pgsodium');
select has_function_privilege('postgres','vault.create_secret(text,text,text)','execute'), has_table_privilege('postgres','vault.decrypted_secrets','select'), has_table_privilege('postgres','vault.secrets','select');
select name from pg_available_extensions where name = 'btree_gist';
```

Attendu : `supabase_vault` et `pgcrypto` installées ; les trois droits à `true` ; `btree_gist` disponible (la migration 3 l'installe).

**Pourquoi :** `supabase db push` applique les migrations une par une. Si `vault.create_secret` échoue (droit manquant, Vault absent), le push s'arrête à la migration 4 (`core_bank_details`) : staging reste à moitié migré (rôles, identité et taux appliqués, le reste non) pendant que Vercel déploie la nouvelle app, qui appelle des RPC qui n'existent pas encore. Mieux vaut le savoir avant de fusionner.

## Mise en service

### Après la fusion, sur staging

D'abord, que le déploiement est complet (lecture seule, éditeur SQL de staging) :

1. **Le job des migrations est vert** (GitHub Actions, déploiement de `main`) et `supabase migration list` montre les 10 migrations appliquées.
2. **Clé de chiffrement** : `select name, created_at from vault.secrets where name = 'pii_encryption_key';` → une ligne. Puis un essai : Paramètres → Coordonnées bancaires, saisir des coordonnées de test, « Afficher », et vérifier la ligne de consultation : `select action, table_name, actor_id, created_at from public.audit_log where action = 'read' order by created_at desc limit 1;` → `read` sur `organization_bank_details`.
3. **Rôles de base** : `select key, org_id from public.roles order by key;` → `admin`, `admin_assistant`, `counselor`, `provider`, tous avec `org_id` nul ; plus de `staff`.
4. **Droits des RPC** : `select has_function_privilege('authenticated', 'public.create_role(text, text)', 'execute');` → `true` ; `select has_function_privilege('service_role', 'public.set_bank_details(text, text, text, text)', 'execute');` → `false`.
5. **Ton accès** : `select rp.permission_key from public.profiles p join public.user_roles r on r.user_id = p.user_id join public.org_role_permissions rp on rp.org_id = r.org_id and rp.role = r.role where p.email = '<ton courriel>' and rp.permission_key in ('roles.manage', 'settings.bank_manage');` → les deux lignes (dans l'app : l'onglet Rôles offre « Nouveau rôle », la section Coordonnées bancaires est visible).
6. **Province** : `select id, name, province from public.organizations;` → `QC`.
7. **Sentry** : vérifier dans Vercel (Production et Preview) si `VITE_SENTRY_DSN` est défini. Sans lui, aucun rapport n'est envoyé (le code ne fait rien sans DSN) ; c'est voulu jusqu'à ta décision, mais il faut le savoir.

Ensuite :

8. **Changement de courriel sécurisé (les deux adresses)** : changer le courriel d'un compte de test et cliquer seulement le lien reçu à la **nouvelle** adresse. Le changement ne doit **pas** se faire avant que le lien de l'**ancienne** adresse soit cliqué aussi (plan Phase 1, Task 1.21 Step 10 ; décision #7). Sinon, me le signaler avant la mise en production.
9. **Journaux de la base, avant de saisir de vraies coordonnées bancaires** : vérifier que `log_parameter_max_length_on_error` = 0, que `log_statement` n'est ni `all` ni `mod`, et que `pgaudit.log_parameter` est désactivé, pour que les arguments des RPC (numéro de compte) n'arrivent jamais dans les journaux. Liste complète : ADR 0004 (`log_min_duration_statement`, `log_parameter_max_length`, `auto_explain.*`, `pgaudit.log`).
10. **Taux de taxes semés** :
   ```sql
   select org_id, tax, rate, effective_from, effective_to from public.tax_rates order by 1, 2, 4;
   select source, count(*) from public.audit_log where table_name = 'tax_rates' group by 1;
   ```
   Attendu : les deux taux par défaut (TPS 0,05 depuis 2008-01-01, TVQ 0,09975 depuis 2013-01-01, ouverts) et la source `migration:core_tax_rates`.
11. **Défauts des rôles copiés du modèle** (`role_permissions`) : `select role, count(*) from public.org_role_permissions group by 1 order by 1;` → `admin` 9, `admin_assistant` 2, `counselor` 1 (aucune ligne pour `provider`).
12. **Pas de 404 « immutable »** : `curl -I https://app.cliniquemana.com/assets/nexiste-pas.js` doit répondre 404 **sans** `Cache-Control: public, max-age=31536000, immutable`. Sinon, un navigateur garderait cette 404 un an : après un retour arrière (rollback) vers le déploiement qui contient ce fichier, l'app resterait cassée pour lui. Les règles d'en-têtes de Vercel ne dépendent pas du code de réponse : si l'en-tête y est, il faut revoir la règle `/assets/(.*)` avant de compter sur les rollbacks.
13. **En-têtes de cache et HSTS** : `curl -I https://app.cliniquemana.com/` doit montrer `Cache-Control: no-cache` et `Strict-Transport-Security` (Vercel l'ajoute sur ses domaines ; à confirmer sur le domaine personnalisé), et `curl -I` sur un vrai fichier de `/assets/` doit montrer `immutable`.
14. **Gestion de la clé de chiffrement, avant la Phase 4 (bloquant pour tout NAS)** : la liste « Before Phase 4 » de l'ADR 0004 : copie de `pii_encryption_key` dans le gestionnaire de mots de passe de la clinique (procédure de restauration), vérification au déploiement qu'un texte chiffré connu se déchiffre, versions de clé et procédure de re-chiffrement. La copie de la clé est prudente dès que de vraies coordonnées bancaires sont saisies : sans elle, une restauration du projet les rendrait illisibles (il faudrait les ressaisir).

### Avant la production

1. **Sourcemaps pour Sentry** : ajouter `@sentry/vite-plugin` avec ton jeton (`SENTRY_AUTH_TOKEN` dans Vercel) et `build.sourcemap: 'hidden'` ; le plugin téléverse les cartes puis les supprime de `dist` (`sourcemaps.filesToDeleteAfterUpload`), pour qu'elles ne soient jamais servies. D'ici là, pas de sourcemaps du tout.
2. **CSP, d'abord en mode rapport** : ajouter dans `vercel.json`, sur `/(.*)`, l'en-tête `Content-Security-Policy-Report-Only` ci-dessous (remplacer l'hôte Supabase par celui de production, et `<hôte DSN Sentry>` par l'hôte de `VITE_SENTRY_DSN`, p. ex. `o123.ingest.us.sentry.io`). Le passer en `Content-Security-Policy` après une à deux semaines sans rapport inattendu. `'unsafe-inline'` pour les styles : sonner insère une balise `<style>` à l'exécution.

   ```
   default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https://vnmbjbdsjxmpijyjmmkh.supabase.co; font-src 'self'; connect-src 'self' https://vnmbjbdsjxmpijyjmmkh.supabase.co wss://vnmbjbdsjxmpijyjmmkh.supabase.co https://<hôte DSN Sentry>; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'; report-uri https://<hôte DSN Sentry>/api/<projet>/security/?sentry_key=<clé publique>
   ```

## Suivis (pas faits en Phase 2)

- **Propagation du fuseau horaire (avant le premier module chargé en dates)** : `setClinicTimezone` modifie une variable de module, et le nouveau rendu après le rechargement de `AccessProvider` n'atteint que les consommateurs du contexte. Des sous-arbres mémoïsés, ou des clés de requête construites avec `getClinicDateString`, peuvent garder l'ancien fuseau jusqu'à un autre rendu. Si le rechargement des accès échoue après un enregistrement de « Région », l'ancien fuseau reste jusqu'au rechargement de la page. Exposer le fuseau par un contexte, ou indexer l'arbre connecté dessus.
- **`FormGrid`** : partager les chaînes de classes `GRID` / `WIDE` des pages de paramètres dans un composant `FormGrid`. (La partie `lazyNamed()` est faite : `lazyPage(load, exportName)`.)
- **Fil d'Ariane des pages de détail (avant la fiche Professionnel, Phase 4)** : un hook `useShellCrumb(label)` (petit contexte) pour « Professionnels / {nom} », dérivé de la même valeur que `usePageTitle`.
- **Variantes service-role pour Facturation** : `tax_rate_on_for_org(org, tax, date)` et `clinic_today_for_org(org)`, réservées au `service_role` (les versions utilisateur renvoient null sans utilisateur). Ajouter aussi « aucune facture n'utilise ce taux » aux conditions de `delete_tax_rate` : la fenêtre de correction de 24 h peut supprimer un taux déjà en vigueur.
- **`Deps` pour l'environnement et `fetch` dans les fonctions serveur** : injecter `Deno.env` et `fetch` dans les helpers de `_shared/` pour les tester sans globals (prévu en Phase 3 : `_shared/deps.ts`, `createHandler(deps)`).
- **Bibliothèque de notifications sur la page de connexion** : sonner (`Toaster` dans `App.tsx`) est encore dans le JS de la page de connexion ; le charger à la demande, puis l'ajouter aux marqueurs de `scripts/check-entry-chunk.mjs`.
- **CSP** et **sourcemaps Sentry** : voir « Avant la production ».
- **Image Postgres locale** : `supabase/postgres:17.6.1.106` a planté quand `authenticated` appelait une fonction sans droit EXECUTE, et sur des helpers plpgsql `pg_temp` avec gestion d'exception dans pgTAP. Ne jamais écrire de tel test ; utiliser `function_privs_are` (conventions BD §10). Revérifier après une mise à jour de la CLI.

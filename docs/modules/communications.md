# Module `communications` (« Communications »)

The clinic's conversations with its clients: the Gmail mailboxes `info@cliniquemana.com` (the clinic's inbox) and `administration@cliniquemana.com` (payments: the Interac notices, read by Facturation later), mirrored in the app and read in « Courriels » (CM1, CM2), the composer and the Gmail send (CM3), « Rédiger avec l'IA » (CM4), and the SMS (batch SM, lane C). Resend keeps the transactional email (invitations, reminders, notices). Plan: [coding plan §11](../plans/2026-10-11-modules-coding-plan.md#11-communications-communications--batches); roadmap [§2.4](../plans/2026-10-11-next-modules-roadmap.md) and §2.4 bis (what PS Hub brings and the flaws fixed); decisions CM-1… in the [decisions log](../plans/2026-10-07-decisions-log.md#communications-decisions-2026-10-12).

- **Registry:** `modules.key = 'communications'` (migration `20261012184051_communications_module`), no dependency besides core (Clients is optional: the thread → client link of CM2b works while it is enabled). It **starts disabled** in every clinic; an admin enables it in Paramètres → Modules.
- **Permissions:** `communications.inbox` (read the shared mailboxes: admin, counselor, admin_assistant), `communications.mailboxes_manage` (connect, disconnect, synchronise, the « Courriels Gmail » settings: admin). `communications.sms` (« Textos »: read the texts, reply, record a consent) and `communications.sms_manage` (Paramètres → Textos, the test text) (SM: admin defaults only, SM-11). Later: `communications.send` (CM3), `communications.ai_draft` (CM4).
- **Frontend:** `src/modules/communications/` (manifest, `index.ts`, `lib/audit-labels.ts`; CM1: `api/mailboxes.ts`, `api/errors.ts`, `hooks/use-mailboxes.ts` `mailKeys`, `lib/mailbox-status.ts`, `schemas/topic.ts`, `pages/GoogleReturnPage.tsx`, `pages/settings/GmailSettingsPage.tsx`; SM: `api/sms.ts`, `api/sms-settings.ts`, `hooks/keys.ts` `smsKeys`, `pages/SmsPage.tsx`, `pages/settings/SmsSettingsPage.tsx`); i18n `modules.communications.*`.
- **Tests:** pgTAP `096_communications_module`, `102_communications_sms`, `103_communications_gmail`; Deno tests of `_shared/gmail/*`, `_shared/google-oidc.ts`, `_shared/sms/*` and each function; Vitest next to each file; Playwright `e2e/communications.spec.ts`, `e2e/sms.spec.ts`.

## CM1: Gmail

Migrations `20261012204037_communications_gmail` (tables, RPCs, jobs) and `20261012204041_core_webhook_events_gmail_provider` (`gmail` joins `webhook_events`' providers and `claim_webhook_event`).

| `mail_labels` | the mailbox's labels (system and user) | RLS as above | no (CM-2) |
| `mail_threads` | one row per Gmail thread with its summary kept by the database (subject, last snippet and sender, counts, unread, labels union) | RLS as above | no (CM-2) |

The upload purpose `mail_attachment` (bucket `documents`, read with `communications.inbox` through `storage-sign`) takes PDF, JPEG, PNG, WebP and Word up to 10 MB; nothing is uploaded from a browser with it.

### RPCs

- **User:** `get_communications_settings()` / `set_communications_settings(p_patch)` (`communications.mailboxes_manage`; `pubsub_topic`, Google's full topic name, and `pubsub_service_account`, the push subscription's service account, both checked: a malformed one is a French P0001 whose HINT names it), `list_mail_connections()` (the caller's visible mailboxes with their sync state, thread and unread counts; never a token).
- **Service role only** (the functions; each takes the org from the database or the verified caller): `get_communications_settings_for_org`, `store_mail_connection` and `disconnect_mail_connection` (actor model, conventions §8b: `p_actor` re-checked as an active member holding `communications.mailboxes_manage`; audit actor and source set), `get_mail_connection_credentials`, `set_mail_access_token`, `set_mail_connection_status`, `request_mail_sync`, `list_mail_connections_to_sync`, `acquire_mail_sync_lease`, `finish_mail_sync`, `reset_mail_history` (refused while another pass holds the lease), `set_mail_watch`, `upsert_mail_labels`, `upsert_mail_messages` (≤ 50 a call; creates the threads and their link rows, keeps a body once stored, recomputes the summaries), `delete_mail_messages`, `apply_mail_label_changes`, `list_mail_attachments_to_store`, `record_mail_attachment`.

### Edge functions

| Function | Category | What |
|---|---|---|
| `gmail-connect` | user (`communications.mailboxes_manage`) | `start` → Google's consent URL for a shared mailbox (CM-10; scopes `gmail.modify` and `gmail.send` only, offline, `prompt=consent`, the fixed redirect `APP_URL/courriels/retour-google`, a signed state: clinic, person, nonce, 10 minutes); `disconnect` → stops the watch (with a refreshed token), revokes the grant, deletes the tokens and the sync state; the mirror stays |
| `gmail-callback` | user (`communications.mailboxes_manage`) | the app's return page posts `{ code, state }` with the session (CM-3): the state's MAC, age and purpose, the same clinic and person, the nonce spent once (`link_invalid` / `link_expired` / `link_used`), the code exchanged, `gmail.modify` required, then `store_mail_connection` |
| `gmail-webhook` | webhook | Pub/Sub's authenticated push at `?org=<id>` (CM-4): one per-IP hit, then Google's signed token verified (`_shared/google-oidc.ts`: keys, issuer, audience `clinique-mana:gmail-push:<org>`, expiry, `email` = the setting `pubsub_service_account`, required), the module gate, `claim_webhook_event('gmail', '<org>:<messageId>')`, the named mailbox matched exactly, then an inline sync (25 s); a held lease fails the claim with 503 so Pub/Sub redelivers |
| `gmail-sync` | user (« Synchroniser », `{ connection_id, full? }`) and job `communications.gmail_sync` (every 15 min) | the sync of `_shared/gmail/sync.ts` (below) |

`_shared/gmail/`: `env.ts` (Google's origins; the local fake's only while `APP_URL` is local), `client.ts` (the Gmail API calls), `credentials.ts` (the OAuth application from the org secrets `google_oauth_client_id` / `google_oauth_client_secret`, the token exchange and refresh; `invalid_grant` → `needs_reconnect`), `mime.ts` (bodies, addresses, parts), `sync.ts`. `_shared/oauth-state.ts` signs and checks the state (HMAC of `INTERNAL_FUNCTION_SECRET`).

**One sync pass** (under the mailbox's 5-minute lease; a second caller is `skipped` and nothing is lost: `sync_requested_at` stays newer than `last_sync_at`): the access token, the labels, then the **first pass** (CM-7: the profile's history id read first, `newer_than:45d`, resumable by its page token) or the **incremental pass** (`history.list`; the history id advances to the largest record applied, CM-6; a 404 / 410 forgets it and runs the first pass again), the attachments still to copy (20 a pass, sniffed, `register_system_file` + upload, 5 attempts; CM-5), the watch, then `finish_mail_sync`. Nothing logs an address, a subject or a body.

**Jobs:** `communications.gmail_sync` and `communications.gmail_watch_renew` (business jobs: **off** until the clinic turns them on), `communications.mail_bodies_purge` (SQL, maintenance, daily 08:45 UTC: bodies and snippets of messages older than 24 months nulled, their files soft-deleted, headers kept; CM-8).

### Frontend

- Paramètres → **Courriels Gmail** (`courriels-gmail`, `communications.mailboxes_manage`): « Boîtes connectées » (each mailbox's state in plain words, last sync, counts, not watched while a topic is set, « Synchroniser », « Reconnecter », « Déconnecter » confirmed, « Connecter une boîte »), « Application Google » (the OAuth client's two secrets, write-only, changed with `settings.integrations_manage`; the redirect URI to copy), « Notifications de Google » (the topic and the service account in one form; the push address and the audience to copy), « Tâches planifiées » (the two jobs through core's `ScheduledJobState`).
- `/courriels/retour-google` (`communications.mailboxes_manage`): Google's return; posts the code and state once (a one-shot query keyed on the state), starts the first sync, then goes back to the settings, replacing the address.

### Local development

## CM2: « Courriels »

Migration `20261013033913_communications_inbox` (pgTAP `109`); decisions CM-11, CM-12.

### RPCs

- **Who reads the mail:** the mirror's content (labels, threads, messages, attachments, links) needs `communications.inbox` (`private.readable_mail_connection_ids`: the clinic's shared mailboxes and the caller's own personal ones). `communications.mailboxes_manage` alone sees the mailboxes (`mail_connections`, CM1's `visible_mail_connection_ids`), never their mail.
- `list_mail_threads(p_connection_id, p_view, p_label_id, p_search, p_before, p_before_id, p_limit)` and `get_mail_thread(p_thread_id)`: **security invoker**, the mirror's RLS (the module gate and `communications.inbox`) is the whole check, so a mailbox the caller cannot read returns nothing. Views `inbox`, `unread`, `starred`, `sent`, `all` (not trash or spam), `label`; keyset pages on `(last_message_at, id)`, 50 by default, 100 at most; the search is `websearch_to_tsquery('french', …)` over the messages' `search_vector` (subject, sender, snippet: never the body), so « facture -interac » and "phrases" work as in Gmail. A thread returns its latest 100 messages, oldest first, with their attachments.
- `get_mail_threads_for_action(p_actor, p_org_id, p_thread_ids)` (service role, for `gmail-modify`): the actor re-checked (an active member holding `communications.inbox`), only the clinic's connected mailboxes she may read, 1 to 50 threads, with the Gmail ids and labels the function needs.

### Edge function

| Function | Category | What |
|---|---|---|
| `gmail-modify` | user (`communications.inbox`) | `{ thread_ids (1–50), action }`: `read`, `unread`, `archive`, `inbox`, `star`, `unstar`, `label` / `unlabel` (a user label of the mailbox). 600 an hour per caller (`gmail.modify_user`: opening an unread thread marks it read). thread by thread, **Gmail first** (`threads.modify` / `messages.batchModify`), then at once its mirror (`apply_mail_label_changes`): the app never shows a state Gmail refused, and a later failure never leaves a change unrecorded; a thread Gmail no longer has is skipped. `{ changed, failed }` (the threads not changed); only when none changed does the first failure answer (409 when Google refuses the mailbox's refresh, which marks it; 502; 500). It sends nothing to anyone: P3-40 does not apply |

### Frontend

- **`/courriels`** (`communications.inbox`, `InboxPage`): from `lg`, three panes: the mailbox (a choice when there are several) and its views with the inbox's unread count, then its own labels (`MailboxNav`); the threads of the view (`MailThreadList`: sender, time, subject, snippet, unread in bold, star, paperclip, « Afficher plus de courriels »); the open thread (`MailThreadView`). On a phone the list, then the thread with « Retour aux courriels ». The address keeps the state (`?boite=`, `?vue=` (`libelle:<id>` for a label), `?q=`, `?fil=`: ids only, never an address or a subject); the search runs over every view 300 ms after the last key. No timer: new mail comes with the sync, and the list is read again when the page is shown.
- **The thread:** the subject takes the focus; unread messages and the latest are open, the others fold to one line. Opening an unread thread marks it read once, silently. Actions (« Archiver » / « Remettre dans la boîte de réception », « Marquer comme non lu », « Suivre », « Libellés » (the thread's own mailbox's), « Ouvrir dans Gmail ») are optimistic, run one after the other (one mutation scope), and roll back with a French toast when Gmail refuses (`useMailAction`, `mailKeys`); a partial answer says how many were not changed. On a phone, « Retour aux courriels » gives the focus back to the row.
- **Received HTML** (`lib/email-html.ts`, DOMPurify 3.4.16): scripts, forms, frames, event handlers and `javascript:` dropped, styles filtered, links opened in a new tab without a referrer; **remote images held** until « Afficher les images » (they would tell the sender the mail was read); `cid:` images resolved through signed URLs. Styles that could fetch from outside are dropped (`url(`, `image-set(`, escapes, comments, image properties). Shown in `SafeEmailHtml`, a sandboxed frame without `allow-scripts` and with `no-referrer`, scaled to the pane when a layout is wider. A browser DOMPurify does not support gets the text, escaped.
- **Attachments:** a stored copy opens through `useSignedFileUrl` (`storage-sign`, P3-33); one the app did not copy (type not accepted, too large, failed) says « dans Gmail seulement » with a link to the thread in Gmail; a purged body (24 months, CM-8) says so.

### The thread → client link (CM2b, CM-12, CM-13)

Migration `20261013102409_communications_client_links` (pgTAP `155`); decisions CM-12, CM-13. The table is CM1's `mail_thread_links` (`unlinked`, `needs_review`, `linked`; `source` `auto` or `manual`); `upsert_mail_messages` writes an `unlinked` row for every thread it creates.

- **Automatic, in the sync:** a statement trigger after insert on `mail_messages` (`mail_messages_link_clients`, transition table) hands each clinic's threads with a new inbound message to `private.communications_link_threads(p_org, p_thread_ids)`: the senders' addresses (never the mailbox's own) go to Clients' `private.clients_match_email` (CL-23); the files whose own address it is win over the files of a related person; one → `linked` (`auto`), several → `needs_review` with the candidates (≤ 20), none → `unlinked`. Only while Clients is enabled for the clinic. A link a person made or undid (`manual`), or an automatic one already linked, is never touched again. Threads mirrored before CM2b are evaluated at their next inbound message; meanwhile they show in « À rattacher ».
- **« À rattacher »:** the view `to_link` of `list_mail_threads` (replaced, same signature): the inbox's threads not linked and never unlinked by a person, newest first. The left pane shows it, and `?vue=to_link` opens it, only for whoever holds `clients.view` (a disabled Clients removes the permission).
- **The thread's file:** `get_mail_thread_link(p_thread_id)` (invoker: the mirror's RLS, then Clients' `clients_directory`) → status, source, the file (`id`, `client_number`, `display_name`) and the candidates. Under the thread's actions (`ThreadClientLink`, `clients.view`): the file « CLI-000042 · Alice Exemple » opening the record, « (trouvé par l'adresse de l'expéditeur) » when automatic, « Détacher », « Changer de dossier »; to review, each candidate (opening its record) with « Rattacher »; otherwise « Rattacher à un dossier ». The search runs Clients' published `search_clients` from 2 characters (name, email, number or phone; 8 results, archived files marked); Communications imports none of Clients' code (it does not depend on it).
- **Manual:** `link_mail_thread(p_thread_id, p_client_id)` / `unlink_mail_thread(p_thread_id)`: definer, `communications.inbox` and `clients.view`, the thread readable by the caller (`private.communications_visible_thread`), the file in `clients_directory` for the same clinic, not merged nor anonymised (P0001, HINT `client_id`); audited (`rpc:link_mail_thread`, `rpc:unlink_mail_thread`), `source = 'manual'`.
- A merge of clients re-points the links and candidates through Clients' `client_merge_handlers` (`private.communications_reassign_client(old, new) → int`); an anonymisation unlinks them and drops the file from the candidates through `client_anonymize_handlers` (`private.communications_anonymize_client(id) → int`).
- React Query: `mailKeys.threadLink(id)` (under `threads()`, so a sync reads it again) and `mailKeys.fileSearch(query)`; a link or unlink invalidates `threadLink(id)` and `threadLists()`.

## CM3: the composer and the Gmail send

Migration `20261013165711_communications_composer` (pgTAP `156`); decisions CM-14 … CM-17. PS Hub's composer is the source (roadmap §2.4 bis: `ComposerCore`, `RichEmailEditor` on TipTap, `TemplatePill`, the client-side delay of ADR 0063), its flaws fixed (no attachment by URL, no file of another clinic, no file lost in silence, no « To » turned into « Cc », no open-tracking pixel).

- **Where:** « Courriels » (« Nouveau message », « Répondre », « Répondre à tous », « Transférer » on the thread, « Brouillons » in the left pane) and a client record's new tab **« Courriels »** (slot `client.messages`, Clients' `MessagesTab`): the file's linked threads and « Écrire un courriel » to the addresses that receive its communications (Clients' `client_contacts_for`). The composer is docked at the bottom right on a computer (« Réduire »), full screen on a phone; it is not modal (Échap does nothing; the X keeps the draft).
- **Drafts (CM-14):** `mail_drafts`, each person's own (RLS: her rows, `communications.inbox`), written by `save_mail_draft` 1.5 s after the last real change (nothing on opening; every id checked: her mailbox, its thread and message, a file of the clinic with `clients.view`, her own uploads or a readable mirrored attachment; at most 50 drafts, 10 files), read by `list_mail_drafts` / `get_mail_draft`, removed by `delete_mail_draft` or the send. Never the browser's storage; closing the composer keeps the draft; a change not saved yet when it goes is saved once more. Not audited (000_invariants: rewritten every few seconds); the send is (`mail_sends`).
- **Templates (CM-15):** the clinic's are core templates of module `communications` (`communications.acknowledgement` « Accusé de réception », `communications.follow_up` « Relance »), edited in Paramètres → Modèles de courriels like every other; each person's own are `mail_templates` (« Enregistrer comme modèle », « Supprimer », 50 per person, audited with the body redacted). `list_mail_compose_templates` lists both. A template replaces the text written (asked first), never the quote; on a new message it also fills an empty subject.
- **Placeholders (CM-15):** `{{person.first_name}}`, `{{person.last_name}}`, `{{sender.name}}`, `{{clinic.name}}` (« Insérer »), filled by `gmail-send` from `prepare_mail_send`'s values (HTML-escaped). An unknown or broken placeholder, or `{{person.…}}` without a file (named, or the thread's link), is refused in French: never a blank sent to a client.
- **The send (CM-16):** « Envoyer » checks the recipients, the subject and the text, saves the draft, then counts **5 seconds** with « Annuler l'envoi » (the message has not left; closing the page meanwhile leaves the draft). Closing the composer during the five seconds sends nothing and says so. Then `gmail-send` (user, `communications.inbox`; 60 an hour per person, 500 a day per clinic) with one key per content (« Envoyer » again on the same message reuses it):
  1. `prepare_mail_send` (service role, the actor re-checked): the mailbox (connected, `gmail.send` granted), the thread and the answered message, 1–150 recipients (at least one « À »), the file, P3-40, the placeholders, the files (≤ 10, 18 MB together: the composer's uploads `mail_outgoing` of the sender (read by her and the mailbox managers only), or attachments of messages of a mailbox she reads; never a URL); the file needs `clients.view` (named, or taken from the thread's link); records `mail_sends` (`pending`; the same key again answers « already sent », refuses while one is running (two at once included), and tries again after `failed`, after `unknown` or after a `pending` older than two minutes, then with `verify_first`).
  2. The files read from our storage (service role, paths from the database); one that cannot be read fails the send.
  3. The HTML hardened, a text alternative, the MIME built on the server (`_shared/gmail/compose.ts`: no CR/LF from the input in a header, RFC 2047 names, RFC 2231 file names, `In-Reply-To` / `References` for a reply), then Gmail `messages.send` (upload endpoint, in the thread for a reply; a forward starts its own). The Message-ID is the send's own (`<send_id@domain>`), the same on every try; invalid References are dropped, a long chain keeps the first and the latest 19, one per folded line. Never retried, never cut short by the browser leaving. Gmail's answer decides: a refusal (4xx) marks the send `failed` (`outcome: refused`); no usable answer (timeout, unreachable, 5xx) marks it `unknown` (`outcome: unknown`), and the next « Envoyer » with the same key first asks Gmail for that Message-ID (`rfc822msgid:`): found, it is closed as sent without a second message.
  4. The sent message mirrored at once (`mirrorMessage`), then `complete_mail_send`: the draft deleted, the uploads kept with the send (subject `mail_send`, no expiry), the new thread linked to the file (manual). A `{{` in someone else's text (the quote, the subject answered) is broken with a zero-width space: never filled, never refused.
- **P3-40 (CM-16):** while Communications, or Clients when the message is about a file, is « Réservé aux testeurs », a message to anyone outside the clinic (an address that is neither an active staff member's nor one of the clinic's mailboxes) is refused in French (HINT `module_reserved`); a tester can still write to the clinic's own people (pgTAP 156).
- **Clients' merge and anonymisation:** CM2b's two handlers also move or clear `mail_drafts.client_id` and `mail_sends.client_id`.
- **The backfill of CM2b (CM-17):** the nightly maintenance job « Rattachement des anciens courriels » (`communications.mail_links_backfill`, `private.job_mail_links_backfill`, « Exécuter maintenant » in Tâches planifiées) hands every thread with inbound mail that no person linked or unlinked, and that is not linked yet, to `communications_link_threads`, 500 at a time; idempotent, and it also links the threads of a file created after its first email, and a thread sent from the app about a file whose immediate mirror failed (manual, unless a person decided).
- **Tests:** pgTAP `156_communications_composer` (70); Deno `gmail-send/handler.test.ts`, `_shared/gmail/compose.test.ts`; Vitest `Composer`, `lib/compose`, `InboxPage` (reply, new message, drafts), `ClientMailPanel`; e2e `communications-inbox.spec.ts` (reply and send through the fake Gmail).

## CM4: « Rédiger avec l'IA » (CM-18 … CM-20)

  - **`ai_settings`** (audited), one row per clinic: on or off, the model (`gpt-5.4`), the monthly cap (50 $) and the prices per million tokens the cost is counted with. **Off until the clinic enters its OpenAI key** (org secret `openai_api_key`, SecretField, `settings.integrations_manage`) and switches it on.

  - **RPCs:** `get_ai_settings`, `set_ai_settings` (switching on refused without the key; French checks), `get_ai_draft_status` (the composer: available, cap reached); for the function, `ai_draft_context_for_service` (the actor's right, the settings, the month's spending, the names to hide: the file's person as gmail-send finds it, the sender, the clinic) and `record_ai_request_for_service`.
- **Edge function `communications-draft`** (user, `communications.ai_draft` and `communications.inbox`; see « Security review » for the correspondents' names):
  - **Limits:** 40 calls an hour per caller (`communications.ai_draft_user`). The monthly cap is a French refusal before any call.
  - **What OpenAI sees** (`mask.ts`): the file's person, the sender and the clinic become the composer's placeholders `{{person.first_name}}`, `{{person.last_name}}`, `{{sender.name}}`, `{{clinic.name}}`, which gmail-send fills at the send. Email addresses, phone numbers and long digit runs become numbered tokens `[[courriel-1]]`, `[[téléphone-1]]`, `[[numéro-1]]`, put back in the answer.
  - **Prompts:** PS Hub's (`prompts.ts`), plus the placeholders to keep and « jamais d'information clinique ». The call is OpenAI Chat Completions with `fetch` (no SDK: ADR 0008), `max_completion_tokens` 3 072, a 45 s timeout.
  - **Answer:** `{ text, subject, history }`. OpenAI's refusals: the credit exhausted or the key refused give a French refusal; a busy service gives 429; anything else gives 502 `provider_error`. Each call is recorded, a failure at 0 $.
  - **Origin:** OpenAI's. `OPENAI_API_BASE_URL` (the local fake, `npm run fake:openai`, port 55398) is honoured only while APP_URL is local.
- **Frontend:**
  - **The bar** (`AiBar`, in the composer when `get_ai_draft_status` says available): « Rédiger avec l'IA » opens the instruction box (Entrée sends, Maj+Entrée goes to the line, Échap closes); in a reply, « Générer une réponse » writes one at once.
  - **The proposal:** « Objet proposé » when the subject is empty, then **« Utiliser »** (it replaces the text above the quote, with « Rétablir » for 10 s in the toast), **« Annuler »** and **« Raffiner »** (one more instruction in the same conversation). These are PS Hub's labels, taken as is (CM-18).
  - **Paramètres → IA** (`ia`, `communications.ai_manage`): the key (SecretField), the settings and the month's use.
- **Tests:**

## Textos (batch SM)

Texts go through the clinic's dedicated SMS channel and number on a **Yeastar P-Series PBX**, by its OpenAPI, the system PS Hub uses (R-73, SM-1). Migration `20261012203302_communications_sms`; decisions SM-1 … SM-13 in the [decisions log](../plans/2026-10-07-decisions-log.md#communications-decisions-2026-10-12). The live setup (the PBX application, the channel, the webhook entry) is in the [status doc](../plans/2026-10-07-status.md) (« Mise en service des textos »).

- **Consent (SM-2, SM-6):** `sms_consents`, one row per clinic and number (E.164): `opted_in` / `opted_out`, how (`source`: staff, sms_reply, import, form), when given and withdrawn (the grant's date is kept after a withdrawal), the optional person (`subject_type`, `subject_id`, for Clients), a note. Audited, the number and the note redacted. **No text leaves to a number without a consent in force**, except the acknowledgement of a withdrawal and an admin's test. The staff records one in « Textos » (`set_sms_consent`): a new consent queues the clinic's consent text (it must contain « ARRÊT »), sent at the next dispatch.
- **Texts (SM-3, SM-8):** `sms_messages`, every text in and out, keyed by the other party's number (the thread; view `sms_threads`). Operational, not audited (listed in `000_invariants`); `communications.sms_purge` nulls bodies and attachment names after 12 months and numbers after 24. Inbound MMS: attachment names, types and sizes only, never downloaded (SM-12).
- **Sending (SM-4, SM-5):** `private.send_sms(org, to, body, kind, …)` is the plug-in a module's definer RPC calls (Rendez-vous's reminders, ADR 0003): it checks the consent and sets `send_after` to the next business hours (Monday–Friday 8–17, clinic time, R-52) unless the text is immediate. The job `communications.sms_dispatch` (function `sms-dispatch`, every 15 minutes, off by default like every business job) claims the due texts (20 per run, 2 at a time; a held text only while the business hours are open, so a backlog never runs into the evening) and sends them; texts claimed but never handed to the PBX (an outage, a setup gap, the run's deadline) are released, `queued` again for the next run (`release_sms_claims_for_service`). A staff reply goes at once through `sms-send`. Nothing to a withdrawn number: the claim fails those `consent_withdrawn`.
- **Keywords (SM-7):** an inbound « ARRÊT », « ARRÊTE », « ARRÊTER », « ARRÊTEZ », « STOP », « DÉSABONNER », « DÉSABONNEZ » or « UNSUBSCRIBE » (alone or as the first word, accents and case ignored), or « CANCEL », « END » or « QUIT » alone, withdraws the consent at once, sends the clinic's reply to a withdrawal and raises the notice `communications.sms_opted_out` (once: a stop word from a number already withdrawn is only recorded); « OUI » / « YES » calls `private.sms_confirmation_hook` (a stub; Rendez-vous replaces it to confirm the next appointment); anything else raises `communications.sms_received` (link `/textos?message=<id>`: the number never goes in a URL).
- **The PBX session (SM-9):** the OpenAPI access and refresh tokens live in Vault (`sms_provider_sessions` holds their ids and expiries); a short database lease serialises refreshes across isolates; a token refused once is replaced once. Each OpenAPI application holds at most 8 live access tokens; the clinic keeps one. A second consumer's token does not invalidate the clinic's, but on a shared application the cap is shared: an OpenAPI application of its own for the clinic, if the PBX's administrator can create one, removes that risk.
- **A shared PBX (SM-13):** the 30031 event names no channel, so `sms-webhook` keeps only the clinic's traffic before any claim: a message or session id the clinic already holds, else the session's DID asked of the PBX (`message_session/get`) must be the clinic's number; anything else is acked `ignored` and nothing is stored. Known gap: a delivery report that reaches the webhook before `sms-send` has recorded the PBX's message id (a race of a second or less) is ignored like another tenant's, and the text stays « Envoyé ».
- **Settings (SM-10):** Paramètres → Textos (`communications.sms_manage`): the PBX address, the application's client id and the clinic's number (`org_module_settings`, keys `sms_base_url`, `sms_client_id`, `sms_did`), the consent text and the reply to a withdrawal (`sms_consent_text`, `sms_opt_out_reply`); the client secret and the webhook secret are org secrets (`yeastar_client_secret`, `yeastar_webhook_secret`; `SecretField`, `settings.integrations_manage`); the webhook address, the last event received, the dispatch job's state and « Envoyer un texto de test » (5 per hour).
- **Functions:** `sms-send` (user: `communications.sms` for a reply, `.sms_manage` for a test; `sms.send_user` 60/h per caller, `sms.test_user` 5/h, then `sms.org_day` 500/day per clinic), `sms-webhook` (webhook: `X-Signature`, base64 HMAC-SHA256 of the raw body, `?org=`, one `webhooks.yeastar_ip` hit first; events 30030, 30031, 30032), `sms-dispatch` (job). Shared code in `_shared/sms/` (`phone`, `yeastar`, `transport`, `send`, `webhook`). Nothing logs or reports a number or a body.
- **« Textos »** (`/textos`, `communications.sms`; a thread is read through `list_sms_thread`, so the number travels in a request body, never in a URL): the threads newest first (number, last text, consent in force, a failed last text), the open thread (received on the left, the clinic's texts on the right with their kind, status and the reason of a failure), « Enregistrer / Retirer le consentement », « Nouveau numéro » (records a consent and opens the thread), and the reply box while the consent is in force. No timer: the page reloads when the bell's polled count changes.
- **Locally:** `npm run fake:yeastar` (127.0.0.1:55393; `_shared/testing/fake-yeastar.ts`), `YEASTAR_BASE_URL` in `supabase/functions/.env` (honoured only while `APP_URL` is local); the seed enables the module and stores the fake's settings and secrets. `POST /__fake/inbound { from, body }` posts a signed client text to the local `sms-webhook`; `POST /__fake/deliver/<msg_id>?status=1|2` a delivery report.

## Security review (2026-10-14)

Migration `20261014042141_communications_security_fixes` (pgTAP `188`); Deno `communications-draft/handler.test.ts`, `_shared/gmail/compose.test.ts`, `_shared/google-oidc.test.ts`.

- **AI draft (CM-19):** `communications-draft` and `ai_draft_context_for_service` also require `communications.inbox`; a thread named must be one the caller reads (a shared mailbox, or her own personal one), else 403. The context returns `correspondent_names` (every display name of the thread's messages: from, to, cc, bcc), which `mask.ts` turns into `[[nom-N]]` tokens, whole and word by word (3 letters or more), whether or not the thread is linked to a file and whether or not the caller holds `clients.view`. A name never rewrites a placeholder or a token already put in. The masked text of the message replied to is sent to OpenAI. Limit: names typed in a new message with no thread are masked only when they are the file's person, the sender or the clinic.
- **PBX settings (SM-10):** `set_sms_settings` refuses (P0001) a change of `sms_base_url`, `sms_client_id` or `sms_did` without `settings.integrations_manage` (they decide where the client secret is sent); the same values sent again pass. A new PBX address deletes the stored session (`sms_provider_sessions`; its tokens leave Vault through the row's trigger). Paramètres → Textos shows the PBX form read-only without that permission.
- **Test texts (SM-6):** `queue_sms_for_service` refuses a test to a number whose consent is withdrawn; the dispatch fails a queued one `consent_withdrawn`. No staff phone number exists in the data (`profiles` has none), so a test is not limited to staff numbers.
- **P3-40 at the dispatch:** while Communications is reserved for its testers, `claim_sms_batch_for_service` fails the queued client texts (every kind but `opt_out_ack` and `test`) with `module_reserved`, so nothing queued before the reservation leaves later.
- **Stop words (SM-7):** a stop word also counts as the text's first word (« STOP merci », « Arrêt svp »); « arrête », « arrêter », « arrêtez », « désabonner », « désabonnez » join « ARRÊT », « STOP », « UNSUBSCRIBE ». « CANCEL », « END », « QUIT » (« Cancel mon rendez-vous ») and « OUI » / « YES » still count only alone.
- **Retention (CM-8):** `communications.mail_bodies_purge` recomputes the summaries of the threads whose messages it purges (their snippet was a copy), deletes the drafts untouched for 24 months and the AI call log (`ai_requests`) older than 13 months; it returns `purged= files= threads= drafts= ai_requests=`. The migration nulls, once, the snippet of the threads whose last message was already purged.
- **Outgoing HTML (`hardenHtml`):** a link or source (`href`, `src`, `action`, `formaction`, `xlink:href`, `background`, `poster`, `longdesc`, `cite`) is kept only when, character references decoded (with or without `;`) and controls and spaces removed, its scheme is `https`, `http`, `mailto`, `tel` or `cid`, or it has none (relative, an anchor). `tel:` is kept: the display sanitiser allows it and signatures use it.
- **Google's keys:** an unknown `kid` reads Google's keys again at most once a minute (`UNKNOWN_KID_REFETCH_MS`), so made-up `kid`s cannot make every push fetch them.
- **Known, by design or deferred:**
  - Shared mailboxes have no per-mailbox access: every holder of `communications.inbox` reads every shared mailbox of the clinic (CM-11).
  - Personal mailboxes are not ready to be enabled: an attachment's file is read with `communications.inbox` alone (upload purpose `mail_attachment`), not with the right to its mailbox, and `store_mail_connection` needs the review's fixes; both come first.
  - A spoofed sender address can auto-link a thread to a client (the automatic link trusts the `From` address); « Détacher » undoes it, and a person's choice is never overridden.
  - PBX ids (`provider_msg_id`, `provider_session_id`) are `bigint` in the database, but the functions read them as JavaScript numbers (a string of up to 18 digits through `Number`): exact up to 2^53 (16 digits), far beyond the PBX's counters. Not changed.

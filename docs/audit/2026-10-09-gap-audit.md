# Audit des écarts — 2026-10-09

**Question (Jonathan):** the record header showed initials although the photo existed; « do we have other things like this in the app that were not done correctly? »

**Scope:** read-only audit of `main` at `e5da8d9` (after PRs #21–#23). Covers module Professionnels, the core screens it uses, the edge functions, the migrations (latest definition of each function), the docs' follow-ups and every TODO/VERIFY marker. Nothing was fixed. Paths are relative to the repo root; `…xyz.sql` is `supabase/migrations/<timestamp>_xyz.sql`.

**Method:** for each read RPC (`get_professional_record`, `professionals_list`, `professionals_directory`, `get_professional_documents`, `get_my_*`, `get_submission_review`, history, compensation), the keys the SQL returns were compared with the Zod parser (`src/modules/professionals/api/*.ts`) and with what the components render. Each saved setting was traced to its readers in SQL, edge functions and the app. Each follow-up in the status doc, module docs, plan and inventory §A was re-checked against the code.

**Sizes:** S = under half a day, M = one to two days, L = more.

**Already in flight:** the record header photo is on the local branch `feat/record-header-photo` (not merged). The French spacing of UI text was fixed by PR #23: `t()` now inserts U+202F, so only text that bypasses `t()` is still listed below (emails, SQL messages, PDF).

## 4. Interne ou dette technique

### T1. Module code touches core tables directly — S each
- `api/contracts.ts:309-317` reads `document_template_versions` from the browser, the only direct read of a core table in `src/modules`. The module also calls core's template-version RPCs itself (`:321-358`) instead of `@/core/signing/api`.
- `email_log` is read directly in `…professionals_insurance_reminders_questionnaire.sql:150-162` and `…professionals_invitation_delivery.sql:210-212`, although `private.latest_subject_email` says « never `email_log` itself ».
- `update public.notifications` in `…insurance_reminders_questionnaire.sql:79-86`. `private.expire_notifications` is a core helper but is defined in a module migration (`…professionals_documents.sql:128`).
- `update public.stored_files` in `…image_consent.sql:574` and `…professionals_submission_access.sql:115`, outside `attach_stored_file`.
- **Fix:** core RPCs/helpers (`list_template_versions`, expire by kind and subject, re-own files), then move the calls.

### T2. Missing rate limits or guards — S each
- `professionals-documents` sends an email with no per-caller limit, unlike `professionals-fiche` / `-invite` / `-submit`.
- `professionals-set-status` has no limit (nor does its peer `users-set-status`).
- `staff-invite` lacks the 5-second per-invitation guard that `professionalInviteFile` has: a double click on « Renvoyer » kills the first link.
- `places` charges the user's quota before the clinic's limit refuses (`places/handler.ts:172-182`).
- Reviewer emails go out in one `Promise.all` to up to 20 recipients (`professionals-submit/handler.ts:155`).
- **Fix:** add `LIMITS` entries; send the reviewer emails two at a time; check the org limit first.

### T3. Notifications not closed in edge cases — S (uncertain)
- `document_to_review` survives deactivation and a newer upload of the same type.
- `documents_missing` keeps its first count all week (dedupe by ISO week).
- A reviewer who owns the file is notified about her own review, which she cannot do (P4-304).
- **Fix:** expire on deactivation and supersession; recreate when the count changes; exclude the owner.

### T4. Historique misses the contract preparation — S
